# 模块层次与依赖关系梳理（按架构分层）

以下分析不沿着业务流程展开，而是从“模块处于什么层、彼此怎么依赖、由谁调用、是否直连数据库”等架构维度解释。

## 分层口径（便于统一理解）

1. 核心业务层（Core Business）
   - 把业务规则与编排落在代码中（创建/更新/评分/解释等）
2. 基础设施层（Infrastructure）
   - 解决落库、事务、异步执行调度、持久化向量存储等“通用能力”
3. 支撑组件（Support Components）
   - 为核心业务提供输入转换或语义检索所需的算法/封装（parser、rag 等）
4. 扩展能力（Extension Capability）
   - 可选/增强型能力（如 hr-agent 的可选 LLM narrator、embedding/chat 的可插拔后端）

---

## 模块逐个说明

### `endpoints`

1. 职责  
   - 对外提供 HTTP 路由、参数校验与响应序列化  
   - 调用对应的 service 完成业务；在某些路由中也会直接做文件上传/解析（例如简历同步上传）  
   - 可创建异步 task（例如 `/api/v1/tasks/*`）
2. 依赖谁  
   - 依赖 `app/services/*`（例如 `job_service/resume_service/matching_service/task_service/hr_agent_service`）  
   - 少数路由直接依赖 `app/parsers/*`（简历同步上传时调用 `extract_text_from_file` / `parse_resume_text`）  
   - 依赖 `app/schemas/*` 定义请求/响应模型与类型
3. 谁会调用它  
   - FastAPI 路由注册：`app/api/v1/__init__.py` 聚合 `endpoints`  
   - 运行时由 HTTP 客户端触发（浏览器/后端调用方）
4. 是否直接访问数据库  
   - 否。数据库访问通过 service/repository/vector_store 等间接发生
5. 层次定位  
   - 核心业务层的“接口边界层”（更像 Application/API 层，而非纯基础设施）
6. 删除后丧失什么能力  
   - 系统无法通过 HTTP 暴露核心业务能力（创建 job/上传 resume/匹配/查询/ask 等）

---

### `services`

1. 职责  
   - 实现核心业务编排：创建/更新业务对象、计算匹配评分、生成结构化解释  
   - 作为 service facade：把 repository（持久化）、parser（结构化输入）、rag/llm（语义与证据）等能力组合起来  
   - 把“业务事件”转化为“异步任务入队”（通过 `task_service.create_task`）
2. 依赖谁  
   - 主要依赖 `app/database/repository/*`（通过仓储完成读写）  
   - 依赖 `app/parsers/*`（如 job 的 `jd_analyzer`，resume 的解析流程）  
   - 依赖 `app/rag/*` 和 `app/llm/embedding.py`（matching semantic、索引构建）  
   - 依赖 `app/services/task_service.py`（入队 task）
3. 谁会调用它  
   - `endpoints`（同步 API）  
   - `app/tasks/*`（异步 task handler 在 Worker 中复用同一套 service 逻辑）
4. 是否直接访问数据库  
   - 不直接写 SQL；数据库访问通常通过 repository 或 `vector_store` 内部的 `get_session_context()` 完成  
   - 但从调用链上看它会间接触达 DB 写入/读取
5. 层次定位  
   - 核心业务层（core business）
6. 删除后丧失什么能力  
   - 核心业务规则与编排全部不可用（job/resume/matching/hr-agent 的主要逻辑消失）

---

### `repository`

1. 职责  
   - 数据访问层（CRUD + 查询）：为 service 提供可复用的持久化接口  
   - 提供 task 的“并发安全取任务”查询能力（`TaskRepository.acquire_next_pending`）
2. 依赖谁  
   - 依赖 `app/database/session.py` 的 `get_session_context()`  
   - 依赖 `app/database/models.py` 的 ORM 模型  
   - 依赖 SQLAlchemy 查询表达式
3. 谁会调用它  
   - `services`（核心业务读写）  
   - `app/tasks/*` 与 `vector_store`（间接需要时）
4. 是否直接访问数据库  
   - 是。repository 通过 SQLAlchemy AsyncSession 与 DB 交互
5. 层次定位  
   - 基础设施层（data access/infrastructure）
6. 删除后丧失什么能力  
   - 无法持久化业务数据（job/resume/candidate/match/tasks/vector 索引）也无法读取结果

---

### `session`

1. 职责  
   - 创建 AsyncEngine/AsyncSession  
   - 提供统一事务边界的上下文管理器：`get_session_context()`（commit/rollback）
   - 提供初始化/关闭数据库连接：`init_db()` / `close_db()`
2. 依赖谁  
   - 依赖 SQLAlchemy async engine  
   - 依赖项目环境变量（`DATABASE_URL` 等）与可选 `dotenv`
3. 谁会调用它  
   - `repositories`  
   - `rag/vector_store.py`（DbVectorStore 使用）  
   - `main.py` 在启动/关闭时调用 `init_db/close_db`
4. 是否直接访问数据库  
   - 是（engine/session 与连接管理）
5. 层次定位  
   - 基础设施层（DB infrastructure）
6. 删除后丧失什么能力  
   - 无法连接/初始化/提交或回滚事务，系统无法读写数据库

---

### `models`

1. 职责  
   - 定义数据库结构与 ORM 映射：`JobModel/CandidateModel/ResumeModel/CandidateJobMatchModel/TaskModel/VectorProfileModel/...`
2. 依赖谁  
   - 依赖 SQLAlchemy DeclarativeBase 与 `app/statuses`  
   - 被 repository/rag/tasks/service 引用
3. 谁会调用它  
   - repository（查询/写入对象）  
   - rag/vector_store 与向量索引任务（读取/写入向量表）  
   - service（依赖字段进行计算）
4. 是否直接访问数据库  
   - 否。它只是定义结构，访问发生在 repository/session/vector_store
5. 层次定位  
   - 基础设施层（ORM schema/data model）
6. 删除后丧失什么能力  
   - ORM 映射缺失，持久化层与向量表无法正确落库/读出

---

### `parser`

1. 职责  
   - 将非结构化输入转换为结构化字段（resume 文本 -> parsed；raw JD -> structured；文件 -> 文本）  
   - 核心是“输入标准化/可解释结构化”
2. 依赖谁  
   - `text_extractor` 依赖外部解析库：`pypdf`、`python-docx`（若未安装会返回空）  
   - `resume_parser`/`jd_analyzer` 主要依赖正则与规则
3. 谁会调用它  
   - `resume`：同步上传（endpoint）与 `resume_task`（worker task）  
   - `job`：`job_service.retry_analyze_job` 调用 `jd_analyzer`
4. 是否直接访问数据库  
   - 否
5. 层次定位  
   - 支撑组件（support components）
6. 删除后丧失什么能力  
   - 无法把 PDF/DOCX 简历解析为 parsed，也无法生成 JD structured

---

### `rag`

1. 职责  
   - 为语义匹配提供两类能力  
     - 构建语义输入：`profile_builder`（把 Job/Candidate 结构化信息拼成可向量化文本、并生成候选人证据 chunks）  
     - 语义检索/相似度与向量持久化：`vector_store`（memory 或 DB-backed）
2. 依赖谁  
   - `vector_store`（DbVectorStore）依赖：`session`、`models`（向量表）  
   - `rag_index_task` 与 `matching_service` 依赖 rag 的接口与产物  
   - `embedding_client` 来自 `llm/embedding.py`
3. 谁会调用它  
   - `matching_service`：semantic_score 与 semantic evidence 检索  
   - `rag_index_task`：将向量与证据 chunks 落库到向量表
4. 是否直接访问数据库  
   - 是（当 `VECTOR_STORE_BACKEND=db` 时），DbVectorStore 通过 `get_session_context()` 访问向量相关表
   - memory 后端不访问数据库
5. 层次定位  
   - 支撑组件（support components），且其中 semantic 维度直接参与匹配核心评分
6. 删除后丧失什么能力  
   - 语义分/语义证据增强消失，RAG 向量索引无法构建或检索，matching 语义部分退化为不可用/固定分支

---

### `llm`

1. 职责  
   - `embedding.py`：把向量化能力抽象成 `EmbeddingClient.embed_texts()`  
   - `chat_client.py`：HR-agent 可选调用外部 LLM 生成结构化 JSON（带失败回退）
2. 依赖谁  
   - embedding 目前依赖纯 Python（debug-hash），可在配置下切换到真实 embedding（未来实现）  
   - chat_client 依赖可选网络请求（OpenAI 兼容 HTTP API）
3. 谁会调用它  
   - rag 索引构建任务：`rag_index_task` 调用 embedding_client  
   - semantic scoring：依赖已落库向量（matching_service 本身不直接 embed）  
   - hr_agent：`hr_agent_service`（可选 LLM narractor）
4. 是否直接访问数据库  
   - 否
5. 层次定位  
   - 扩展能力（extension capability）  
   - 其中 embedding 是 RAG/索引构建的关键组成
6. 删除后丧失什么能力  
   - 向量索引无法生成（embedding 缺失）  
   - hr-agent 的可选 LLM narrator 生成能力缺失（grounded 仍可工作）

---

### `hr_agent`

1. 职责  
   - HR Copilot：在匹配解释/语义证据的基础上回答问题  
   - 采用 grounded 优先：默认不依赖外部 LLM；开启后可调用 chat_client 进行叙述增强并严格校验与回退
2. 依赖谁  
   - 依赖 repositories：`job_repository`、`candidate_repository`、`match_repository`  
   - 依赖 `app.schemas.match.MatchExplanation` 与语义证据结构  
   - 依赖 `chat_llm_client`（可选）
3. 谁会调用它  
   - `endpoints/hr_agent.py`（`POST /hr-agent/ask`）
4. 是否直接访问数据库  
   - 间接访问（通过 repositories）
5. 层次定位  
   - 扩展能力（extension capability / Copilot 增强层）
6. 删除后丧失什么能力  
   - `/hr-agent/ask` 问答与叙述增强不可用

---

### `tasks`

1. 职责  
   - 异步任务的 handler：在 Worker 中执行某类任务（resume_upload/matching_run/*_index_build）  
   - 本质上复用已有 service + rag/parser 逻辑，实现“异步化”
2. 依赖谁  
   - 依赖对应的 service（resume_service/matching_service/task_service 等）  
   - 索引类任务依赖 rag、embedding、repository（通过 service/直接组件）
3. 谁会调用它  
   - `worker` 的 `dispatch_task(task)` 按 task_type 调用
4. 是否直接访问数据库  
   - 通常不直接写 SQL，但会通过 service/repository/vector_store 间接访问 DB
5. 层次定位  
   - 基础设施层（异步执行的任务实现）
6. 删除后丧失什么能力  
   - 异步 resume 解析、异步 matching、向量索引构建均无法执行

---

### `worker`

1. 职责  
   - 作为后台执行进程：轮询 tasks 表、并发控制、分发到 tasks handler  
   - 支撑多实例安全消费（SKIP LOCKED）
2. 依赖谁  
   - 依赖 `task_repository.acquire_next_pending` 与 `task_service`  
   - 依赖 `app/tasks/*` handler（dispatch）
3. 谁会调用它  
   - 由运维/启动脚本启动：`python -m app.workers.task_worker`
4. 是否直接访问数据库  
   - 间接访问（通过 task_repository 与 init_db/close_db）
5. 层次定位  
   - 基础设施层（async execution infrastructure）
6. 删除后丧失什么能力  
   - tasks 永远不会被消费，异步任务、索引构建无法完成（系统依赖的 semantic 将长期缺失）

---

## 依赖方向列表（总结）

使用箭头表示“依赖/调用”方向：

- `endpoints` -> `services`
- `endpoints` -> `task_service`（创建 tasks）
- `endpoints` -> `parsers`（仅同步简历上传等路由直接解析）
- `services` -> `repository`
- `services` -> `parsers`（job structured/retry、resume 解析流程等）
- `services` -> `rag`（matching semantic 与解释证据）
- `services` -> `llm/embedding`（索引构建时）
- `rag_index tasks` -> `llm/embedding` 与 `rag/vector_store`
- `repository` -> `session`
- `repository` -> `models`
- `rag/vector_store (DbVectorStore)` -> `session` 与 `models`
- `hr_agent_service` -> `repositories`（job/candidate/match）
- `hr_agent_service` -> `llm/chat_client`（可选）
- `worker` -> `task_repository`（取 pending、并发安全）
- `worker` -> `task handlers (tasks/*)`（dispatch）
- `task handlers` -> `services`（复用业务逻辑）
