# HR Resume System：模块分层架构梳理（整体视图）

本文件只做整体结构梳理，不展开实现细节。依据当前代码组织方式，将系统拆为五层：API 层、Service 层、Repository/DB 层、RAG/LLM 层、Task/Worker 层。

---

## 1) 模块分层

### 1.1 API 层

**职责**

1. 暴露 HTTP 接口（路由、参数校验、响应序列化）。
2. 接收用户意图后，调用对应的 Service 方法（必要时创建异步 Task）。
3. 不承担业务数据治理、评分/解释计算、向量落库等职责。

**主要文件夹**
- `app/api/v1/endpoints/`（jobs / resumes / candidates / matching / tasks / hr-agent）
- `app/api/v1/__init__.py`（聚合所有 endpoint router）
- `app/main.py`（FastAPI 启动生命周期）

**核心类/函数（入口）**
- `app/api/v1/endpoints/jobs.py`：`create_job`、`retry_analyze_job`
- `app/api/v1/endpoints/resumes.py`：`upload_resume`（同步模式：上传->解析->绑定）
- `app/api/v1/endpoints/matching.py`：`run_matching`、`get_matches_by_job`
- `app/api/v1/endpoints/tasks.py`：创建异步任务（`resume-upload`、`matching-run`）
- `app/api/v1/endpoints/hr_agent.py`：`ask`

**与上下层依赖关系**

- 依赖：Service 层（job_service / resume_service / matching_service / task_service / hr_agent_service）
- 非依赖：直接访问 Repository 或 VectorStore（当前 endpoint 均通过 service 间接访问）

---

### 1.2 Service 层

**职责**
1. 业务编排：完成“业务对象的创建/更新/绑定/状态流转”与“评分/解释的计算”。
2. 组织跨模块调用：Repository（持久化）、Parser（结构化输入）、RAG/LLM（语义证据与可解释信息）、TaskService（异步化后续步骤）。
3. 作为系统的主要业务入口面向 API 层。

**主要文件夹**
- `app/services/`

**核心类/函数**
- `JobService`（`app/services/job_service.py`）
  - 创建/更新 Job
  - 对 raw JD 的结构化解析入口（`retry_analyze_job`）
  - “建索引”任务的入队（最佳努力）
- `CandidateService`（`app/services/candidate_service.py`）
  - 创建 Candidate（工具/脚本/后续扩展）
  - 候选人画像建索引任务的入队
- `ResumeService`（`app/services/resume_service.py`）
  - 创建 Resume 记录、保存解析结果、更新状态
  - 将 Resume 的 parsed 字段同步到 Candidate（`bind_candidate_from_resume`）
  - “简历证据/向量索引”任务的入队
- `MatchingService`（`app/services/matching_service.py`）
  - 对某 Job 与 Candidate 集合执行多维匹配（`run_matching`）
  - 拉取某 Job 的匹配结果（`get_matches_by_job`）
  - 调用 VectorStore 获取语义分与证据
- `TaskService`（`app/services/task_service.py`）
  - 对 TaskRepository 的 CRUD/状态封装
  - 提供“创建/标记运行中/完成/失败”的统一入口
- `HrAgentService`（`app/services/hr_agent_service.py`）
  - 基于结构化的 Job / MatchingExplanation / semantic evidence 提供“HR Copilot”式问答
  - LLM 作为可选的叙述层（失败回退到 grounded 输出）

**与上下层依赖关系**

- 依赖 Repository/DB 层：持久化与查询（job_repository / candidate_repository / resume_repository / match_repository / task_repository）
- 依赖 RAG/LLM 层：通过 `app/rag/vector_store.py` 与 embedding/证据生成链路拿到语义分与证据片段
- 依赖 Parser（作为输入规范化/结构化工具）：JD 结构化、Resume 文本提取与 Resume 字段抽取
- 依赖 Task/Worker 层：通过 TaskService 入队异步索引任务（不直接运行 Worker）

---

### 1.3 Repository / DB 层

**职责**

1. 作为数据访问层，使用 SQLAlchemy AsyncSession 对业务表进行 CRUD 与条件查询。
2. 管理事务边界：由 `get_session_context()` 统一 commit/rollback 行为。
3. 不包含评分、向量检索策略等“业务规则”，仅提供持久化读写能力。

**主要文件夹**

- `app/database/session.py`（AsyncSession / engine / init_db / close_db）
- `app/database/models.py`（ORM 模型：Job / Candidate / Resume / CandidateJobMatch / VectorProfile / Chunk 等）
- `app/database/repository/`（各仓储类：job_repository 等）

**核心类/函数**

- `get_session_context()`（`app/database/session.py`）
- `JobRepository`（`job_repository`）
- `CandidateRepository`（`candidate_repository`）
- `ResumeRepository`（`resume_repository`）
- `MatchRepository`（`match_repository`）
- `TaskRepository`（`task_repository`）
  - 支持 `acquire_next_pending()`，用于 Worker 多实例并发消费

**与上下层依赖关系**
- 被 Service 层依赖：Service 用 Repository 完成落库/查询。
- 被 RAG/VectorStore 依赖：`DbVectorStore` 也是通过 `get_session_context()` 访问向量相关表。
- 不反向依赖：Repository 不依赖 API/Service 的业务逻辑。

---

### 1.4 RAG / LLM 层

**职责**
1. 提供“语义化”的能力：将 Job/Candidate/Resume 信息转为向量表达，并进行相似度计算。
2. 为匹配解释提供语义证据片段（semantic evidence）。
3. LLM 仅作为可选能力：hr-agent 的叙述层（grounded 主路径不依赖 LLM）。

**主要文件夹**
- `app/rag/`
  - `vector_store.py`：向量存储抽象（内存版 / DB 持久版）与检索接口
  - `profile_builder.py`：构建语义文本、候选人证据 chunk 等确定性输入
- `app/llm/`
  - `embedding.py`：EmbeddingClient（当前 debug/可插拔）
  - `chat_client.py`：ChatLLMClient（OpenAI 兼容；失败回退）
- `app/parsers/`（定位为支撑模块；见下方“parser 的角色”）

**核心类/函数**
- `vector_store`（`app/rag/vector_store.py`）
  - 支持 backend：`VECTOR_STORE_BACKEND=memory|db`
- `DbVectorStore`（DB-backed 向量落库与检索）
- `build_job_semantic_text` / `build_candidate_semantic_text`
- `build_candidate_chunks`（候选人证据 chunk 生成）
- `embedding_client.embed_texts`
- `chat_llm_client.generate_json`

**与上下层依赖关系**

- 被 Service 层依赖：MatchingService 通过 VectorStore 获取语义分/证据；索引任务通过 profile_builder 与 embedding 客户端落库向量。
- 由 Task/Worker 层驱动落地：RAG 索引任务在 Worker 中执行（见 Task 层）。
- LLMClient 由 HrAgentService 可选调用（作为 grounded 的可选增强）。

---

### 1.5 Task / Worker 层

**职责**
1. 把耗时步骤异步化（例如：简历解析与绑定、向量索引构建、全量匹配）。
2. 提供多进程并发安全消费（`SELECT ... FOR UPDATE SKIP LOCKED`）。
3. 统一任务状态：pending / running / completed / failed。

**主要文件夹**
- `app/api/v1/endpoints/tasks.py`（任务创建 API）
- `app/services/task_service.py`（任务服务封装）
- `app/database/repository/task_repository.py`（任务表持久层与并发消费）
- `app/tasks/`（任务处理器：resume_upload / matching_run / rag index build）
- `app/workers/task_worker.py`（Worker 主循环 + dispatch）

**核心类/函数**
- `task_worker.worker_loop()`：轮询并调度任务
- `dispatch_task()`：按 `task_type` 分发
- `handle_resume_upload()`：上传后执行解析/绑定链路
- `handle_matching_run()`：执行匹配链路
- `handle_*_index_build()`：执行 RAG 索引落库

**与上下层依赖关系**
- 依赖 Service 层：任务处理器通常调用对应的业务 Service 完成落库/业务编排。
- 依赖 Repository/DB 层：通过 TaskRepository 消费任务、写回状态。
- 被 API 层依赖：API 创建任务并返回 task id 供轮询。

## 2) 四条链路归属与“经过哪些层”

为便于理解，下列“链路”指：`job`、`resume`、`matching`、`task` 四条主流程（含异步变体）。

### 2.1 Job 链

**发起层**：API 层  
**经过层**：
1. Service 层：`JobService.create_job` / `JobService.update_job`
2. （结构化解析发生时）Service 层：`JobService.retry_analyze_job` 调用 `parsers/jd_analyzer.py`
3. Repository/DB 层：`job_repository` 落库/更新 Job 的 structured 与状态
4. Service 层：入队 `job_profile_index_build`（TaskService）
5. Task/Worker 层：Worker 执行 `rag_index_task.handle_job_profile_index_build`
6. RAG/LLM 层：profile_builder 构建语义文本 + embedding_client 生成向量 + vector_store 落库
**落点**：
- Job 表（`jobs`）
- 向量配置表（`vector_profiles`，entity_type=job）

---

### 2.2 Resume 链

**发起层**：API 层（同步上传）或 Task/Worker 层（异步上传任务）  
**经过层**（同步变体）：
1. API 层：`/resumes/upload` -> `ResumeService.create_resume_record`
2. Service 层：保存解析结果、状态流转（`resume_service.save_parsed_resume` 等）
3. Parser 支撑模块：`text_extractor` 提取文本、`resume_parser` 抽取结构化字段
4. Service 层：`resume_service.bind_candidate_from_resume` 同步候选人画像
5. Repository/DB 层：`resume_repository`、`candidate_repository` 落库
6. Service 层：入队 `resume_index_build`
7. Task/Worker 层：Worker 执行 `rag_index_task.handle_resume_index_build`
8. RAG/LLM 层：build_candidate_chunks + embedding 落库到 resume chunk 向量表
**落点**：
- Resume 表（`resumes`，parsed 与 status/error_message）
- Candidate 表（`candidates`，通过 bind 补齐字段）
- 向量证据表（`resume_chunk_embeddings`）

---

### 2.3 Matching 链

**发起层**：API 层（同步）或 Task/Worker 层（异步 matching-run）  
**经过层**：

1. API 层：`/matching/run` 或创建 `matching_run` Task
2. Service 层：`MatchingService.run_matching`
   - Repository/DB 层：`job_repository`、`candidate_repository`、`match_repository`
   - RAG/LLM 层：通过 `vector_store` 取 job/candidate profile 向量，并对候选子集做语义相似度与证据抽取
3. Repository/DB 层：将评分与解释（MatchExplanation + semantic evidence）写入 `candidate_job_matches`
**落点**：
- 匹配结果表（`candidate_job_matches`）
- API 查询则通过 `MatchingService.get_matches_by_job` 读取匹配结果（并带候选人字段/解释）

---

### 2.4 Task 链（任务本身的生命周期）

**发起层**：API 层 或 Service 层（入队索引任务）  
**经过层**：
1. API 层：`/tasks/*` 创建任务 -> `TaskService.create_task`
2. Repository/DB 层：`task_repository.create` 写入 tasks 表
3. Task/Worker 层：Worker 主循环轮询 `task_repository.acquire_next_pending` 获取 pending 任务（并切换为 running）
4. Task/Worker 层：调用 `app/tasks/*` 中的具体 handler
5. Handler 内部：通常会再调用 Service 层完成业务落库/业务状态变化
6. Task/Worker 层：handler 通过 TaskService 更新任务状态（completed/failed）
**落点**：
- 任务表（`tasks`）
- 业务对象表（jobs/candidates/resumes/candidate_job_matches）
- 向量表（vector_profiles / resume_chunk_embeddings，来自索引任务）

## 3) session / parser / hr_agent 的角色定位

### 3.1 `session`
**角色**：Repository/DB 层的事务与连接管理（基础设施）  
**类型**：横切基础设施模块（支撑所有需要 DB 的层）  
**是否主链路**：不直接参与 job/resume/matching 的业务规则计算，而是为 repository 与 vector_store 提供事务边界与提交/回滚。

### 3.2 `parser`
**角色**：把“非结构化输入”转换为“结构化字段”的支撑模块  
**包含**：
- `parsers/text_extractor.py`：文件 -> 纯文本
- `parsers/resume_parser.py`：Resume 文本 -> parsed 字段
- `parsers/jd_analyzer.py`：raw JD 文本 -> structured 字段
**是否主链路**：是 job 与 resume 链路的上游支撑输入；但不属于匹配评分本体（matching 的核心规则在 `MatchingService` 内）。

### 3.3 `hr_agent`
**角色**：HR Copilot 问答/润色式增强（建立在结构化证据之上）  
**类型**：支撑模块（在主业务“匹配评分与落库”完成后提供解释型交互）  
**是否主链路**：不是 matching 的发起者，也不是核心评分规则的一部分；它读取 Job 与 Matching 解释证据，然后可选调用 LLM 叙述层（grounded 输出作为主路径回退）。

---

## 4) 核心业务模块 vs 横切基础设施模块

**核心业务模块（主模型/主规则）**
1. Job：`JobService` + `JobRepository` + `JobModel`
2. Candidate：`CandidateService` + `CandidateRepository` + `CandidateModel`
3. Resume：`ResumeService` + `ResumeRepository` + `ResumeModel`
4. Matching：`MatchingService` + `MatchRepository` + `CandidateJobMatchModel`

**横切基础设施模块（复用型能力）**
1. 数据访问与事务：`database/session.py` + `database/repository/*`
2. 异步任务编排：`task_worker.py` + `tasks/*` + `task_repository.py` + `task_service.py`
3. 向量与语义证据：`rag/vector_store.py`、`rag/profile_builder.py`
4. Embedding 与可选 LLM：`llm/embedding.py`、`llm/chat_client.py`
5. 文本到结构化：`parsers/*`（为核心链路提供输入标准化）

## 6) 模块关系表（按链路归属）

| 链路/模块 | 发起层 | 经过层（从上到下） | 落点（主要数据/输出） | 类型 |
|---|---|---|---|---|
| job 链 | API 层 | API -> Service(Job) -> Repository(DB) ->（可选）Parser(JD) -> Task 入队 -> Worker -> RAG(向量落库) | `jobs`、`vector_profiles(entity_type=job)` | 核心业务 |
| resume 链 | API 层（同步）或 Worker（异步） | API/Worker -> Service(Resume) -> Parser(Text+Resume) -> Service(绑定 Candidate) -> Repository(DB) -> Task 入队 -> Worker -> RAG(证据向量落库) | `resumes`、`candidates`、`resume_chunk_embeddings` | 核心业务 |
| matching 链 | API 层（同步）或 Worker（异步） | API/Worker -> Service(Matching) -> Repository(DB) -> RAG(Vector similarity/evidence) -> Repository(DB) | `candidate_job_matches` | 核心业务 |
| task 链 | API 层（创建任务）或 Service 层（入队索引任务） | API/Service -> TaskService -> Repository(DB: tasks 表) -> Worker -> Task handler -> Service/Repository/RAG | `tasks` + 业务表 + 向量表（取决于 task_type） | 横切基础设施 |
| session | Repository/DB 层（被调用方视角） | Service/RAG/Worker -> Repository -> DB session context -> commit/rollback | 保障所有 DB 写入一致性 | 横切基础设施 |
| parser | job/resume 链上游 | Service(Job/Resume) -> parsers/* | `Job.structured`、`Resume.parsed` | 支撑模块（输入规范化） |
| hr_agent | API 层（`/hr-agent/ask`） | API -> Service(HrAgent) ->（读取证据）->（可选）LLM chat_client -> 输出回答 | 生成 grounded/可选 LLM 叙述结果（非核心评分落库） | 支撑模块（Copilot 增强） |
