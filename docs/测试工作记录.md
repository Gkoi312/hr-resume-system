### 伴随改动：别名映射表修正

**文件**：[`app/parsers/resume_parser/skill_evidence.py`](../app/parsers/resume_parser/skill_evidence.py)

**问题**：原别名表把上下位关系当同义词处理。

| 原映射 | 问题 |
|--------|------|
| django → python | 框架 ≠ 语言，信息降级 |
| fastapi → python | 同上 |
| postgresql → sql | 具体 DB ≠ 通用概念 |
| vue/react → javascript | 框架 ≠ 语言 |
| k8s → docker | 不同产品，映射错误 |
| springboot → java | 框架 ≠ 语言 |

**后果**：`["Python", "FastAPI", "PostgreSQL"]` 三个技能要求在别名归并后只剩 `["python", "sql"]` 两个。打分分母从 3 变成 2，结果失真。

**修复原则**：只归并确凿的"同物异名"（k8s=kubernetes、golang=go、nodejs=node.js），框架、库、工具各保持独立 canonical。

**验证**：新增 3 条反向验证测试（django≠python、postgresql≠sql、vue≠javascript），全部通过。

### 第五轮：规则版经历质量评分 + LLM 降级（2026-06-28）

**背景**：HR 扫简历时虽然看不太懂技术细节，但能判断谁的实习/项目**写得好**（描述具体、有数据、有成果）vs **写得差**（一句带过、空洞）。原来用 LLM 做这个判断成本高（一个候选人一次 API 调用），需要降级为规则版。

**新增文件**：[`app/services/experience_quality_scoring.py`](../app/services/experience_quality_scoring.py)（~320 行）
**新增测试**：[`tests/test_experience_quality_scoring.py`](../tests/test_experience_quality_scoring.py)（19 条用例）

**评分四维度**：

| 维度 | 权重 | 测什么 | HR 对应行为 |
|------|------|--------|-------------|
| 内容充实度 | 35% | 描述长度、是否有内容 vs 空/一句话 | 扫一眼就知道这人写了多少 |
| 具体性 | 30% | 数字/百分比、动作-结果模式 | 有数据的描述比空泛的更可信 |
| 公司认可度 | 20% | 是否在知名公司（腾讯/字节/Google…）实习过 | 大厂名 = 强信号 |
| 经历广度 | 15% | 实习数、项目数、是否有技能标签/自我描述 | 经历越多越立体 |

**具体性检测机制**：
- **数字/指标**：正则匹配 `100万用户`、`QPS 5000`、`提升了40%`、`P99 < 10ms` 等 20+ 中英文模式
- **动作-结果**：正则匹配 `负责…开发`、`主导搭建…平台`、`通过…将…降低` 等中文句式
- **组合加分**：同一段描述中既有数字又有动作结果，额外 +15

**公司名单**（100+ 条目，分三档）：
- Tier 1 (10分)：腾讯、阿里、字节、Google、Microsoft、OpenAI…
- Tier 2 (7-9分)：美团、京东、快手、商汤、大疆、小红书…
- Tier 3 (5-6分)：联想、IBM、Oracle、知乎、携程、中金…

**LLM 降级逻辑**（`matching_service.py`）：
- `MATCH_LLM_ENABLED=1` → 走 LLM（保留原路径）
- 默认不设置 → 走规则版（无 API 成本、毫秒级延迟）
- 两种模式返回结构兼容，`LLMQualityBreakdown` schema 不变

**改动文件**：
- 新增：`app/services/experience_quality_scoring.py`
- 新增：`tests/test_experience_quality_scoring.py`
- 改动：`app/services/matching_service.py`（`_pros_cons_recommendation` 适配规则版、`run_matching` 中启用条件分支）

**测试覆盖**：公司名匹配（精确/模糊/未知）、描述具体性（空/模糊/有指标/有动作/两者都有）、空候选人/弱候选人/强候选人端到端打分、返回结构兼容性验证。

### 第八轮：消融实验 + 打分公式重构（2026-06-28）

**为什么做**：skills 40% + semantic 20% + quality 40% 的加权公式没有经过验证——各维度权重是否为最优，语义分到底有没有增量贡献，全都靠直觉。

**消融实验**：15 个岗位 × 40 个候选人，固定原始分（技能/语义/质量各算一次），换不同权重配置重新融合排名，对比 ground truth 的 NDCG/Precision/Recall。（评测脚本与数据集已移除，结果保留在 README 评测结果章节。）

**关键结论**：

| 配置 | NDCG@5 | 结论 |
|------|--------|------|
| Skill×Quality（新公式） | **1.0000** | 15/15 岗位最优 |
| SkillOnly（纯关键词） | 0.9948 | 14/15 最优 |
| NoSem→Skill | 0.9828 | 去掉语义反而更好 |
| Baseline（旧公式） | 0.9747 | 被全面超越 |
| SemanticOnly | 0.8545 | 有信号但漏人 |
| QualityOnly | 0.2347 | 基本随机（岗位无关） |

**语义分为什么没用**：它本质是岗位职责描述和候选人项目描述在向量空间里的相似度。Ground truth 按技能关键词 overlap 定义，语义分和技能分不完全相关，混进排名就是加噪声。而且它是最慢的一步（62ms，占 50% 耗时）。

**质量分为什么不能做加法维度**：质量分是岗位无关的——一个候选人无论投什么岗位质量分都一样。按质量分排名就等于「谁简历写得最长谁排前面」，和技能匹配完全正交。但它作为**乘法系数**有用——技能分决定排序上限，质量分决定可信度折扣。

**最终公式**：

```
overall = skill_score × quality_factor
quality_factor = 0.6 + 0.4 × (quality_score / 100)   # 范围 [0.6, 1.0]
```

**效果**：
- 技能满分 + 有证据 → 75-82（推荐面试）
- 技能满分 + 注水简历 → 64（备选，被惩罚）
- 技能一般 + 写再好 → 20-40（不推荐，写得好救不了不匹配）

**改动文件**：
- [`app/services/matching_service.py`](../app/services/matching_service.py) — 公式从三维加权改为 Skill×Quality；推荐阈值下调（80→70, 60→50, 40→35）
- [`app/schemas/match.py`](../app/schemas/match.py) — `ScoreBreakdown` 去掉 3 个 weight 字段，新增 `quality_factor`
- [`demo/components/match_card.py`](../demo/components/match_card.py) — 前端分数展示适配新公式，语义标记为「仅供参考」

## 设计原则（本轮确立）

1. **测匹配逻辑，不测框架行为**。`TestClient` 验证的是 FastAPI 的请求分发是否正常；真正可能出错的是打分函数里一个除法、一个去重、一个阈值判断。这些才是单测该抓的。

2. **贴近 HR 真实工作方式**。不要为了算法的"精巧"而偏离筛选实践。技能匹配就是关键词命中，不需要把 django 降级成 python 再来计数。LLM 质量分比语义分块匹配对 HR 更有用。

3. **纯函数优先**。能不连 DB、不调 LLM、不启动服务的，全部用构造数据测试。跑得快、确定性高、改代码时反馈即时。

4. **反向验证是正向测试的一部分**。每次修 bug 或改设计（如别名表），同时加一条"确认旧错误不再发生"的测试，防止回退。
