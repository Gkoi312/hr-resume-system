# 面试要点与项目亮点

## 项目概述（30秒版本）

> 面向校招/实习场景的 **HR 简历智能筛选系统**——HR 上传 JD 和简历后，系统自动做学历硬过滤 + 多轴语义匹配打分，输出带证据片段的可解释排序结果。后端用 FastAPI + PostgreSQL/pgvector，匹配核心是自己实现的 BM25+Embedding 混合检索 + RRF 融合。

---

## 面试可能会问的 5 个问题

### Q1: 为什么要做混合检索（BM25 + 向量 + RRF）而不是纯向量？

**问题背景**：纯 embedding 做中文简历-JD 匹配有缺陷——向量擅长语义近似，但对**精确术语匹配**（如「Docker」「Kubernetes」「分布式」）不够敏感。

**我的方案**：
- **BM25**：基于 jieba 中文分词（自定义词表含「后端」「校招」等 HR 术语），做词袋精确匹配
- **向量余弦**：用 BGE/sentence-transformers 做语义相似度
- **RRF（Reciprocal Rank Fusion）**：将两个排名的倒数做加权融合，不依赖绝对分数归一化

**具体应用**：在 Delivery 轴（岗位职责 ↔ 候选人经历对齐），对每条职责找最佳经历的流程：
1. 计算所有 (职责, 经历) 对的 cosine 和 BM25
2. 分别排 rank，RRF 融合后选最优对
3. 返回对齐明细表（含 shared_terms 重合词），HR 可审计

**为什么不只用 LangChain/现成方案**：可控性强、无黑盒依赖、适合校招场景的术语匹配。

---

### Q2: 打分架构为什么是三层（规则 + 语义 + LLM）而不是一个端到端 LLM？

**设计原则**：**硬门槛规则化、语义用于排序、LLM 仅做辅助**。

三层分工：
| 层 | 权重 | 做什么 | 为什么不用 LLM 做 |
|------|:--:|------|------|
| 技能规则分 | 30% | 标准化关键词语义匹配 + 同义词映射 | 规则可审计，技能命中/缺失一目了然 |
| 语义综合分 | 40% | 向量 + BM25 混合，技能/Delivery/角色三轴 | 可解释对齐明细；LLM 判断匹配度不稳定 |
| LLM 质量分 | 30% | 评估候选人经历描述的 impact/evidence/consistency | 这里 LLM 有价值但非决定性 |

**为什么不做端到端 LLM**：
1. LLM 对同一份简历可能给出不同分数（非确定性）
2. 校招场景重视**公平性和可审计性**
3. 结构化解释比自然语言总结更便于 HR 复核

---

### Q3: 异步任务系统为什么用数据库队列而不是 Redis/RabbitMQ？

**场景分析**：校招场景的简历批处理量大但非实时——上传 100 份简历后批量跑匹配，不需要毫秒级调度。

**数据库方案**：
- `SELECT ... FOR UPDATE SKIP LOCKED` — 多 worker 实例安全取任务
- 无需额外中间件依赖，部署简单
- 匹配任务本身就是 DB-heavy，任务和结果在同一个事务里

**代价**：轮询有固定延迟（默认 5s），高并发下不如专业 MQ。但对于这个场景足够了。如果量级扩大，后续可无缝替换为 Redis Streams。

---

### Q4: 为什么用 Candidate（候选人主档）而不是 Resume（简历文件）作为匹配核心？

**数据模型设计**：
- 一个候选人可能有多份简历（不同版本、不同岗位投递）
- HR 可能手动编辑候选人的技能/经历（不覆盖已更新字段）
- 匹配时以 Candidate 主档为准，Resume 的 parsed 数据仅用于「补缺」

**回填策略**：`bind_candidate_from_resume` 仅在对应字段为空时才写入，保护 HR 已编辑数据。这避免了「重新解析简历覆盖了 HR 手动修正」的问题。

---

### Q5: 学历过滤为什么放在语义匹配之前？

**性能与公平性**：
- 学历不满足的候选人直接排除，不参与昂贵的向量计算
- 硬门槛规则化——学历等级（大专/本科/硕士/博士）从简历结构化提取，不依赖 LLM 判断
- 过滤结果和证据可审计（在 `education-filter` 预览端点可直接查看）

## 技术亮点

### 1. 自研混合检索（BM25 + Embedding + RRF）
- 纯 Python 实现 Okapi BM25（无外部搜索引擎依赖）
- jieba 自定义词表适配 HR 领域术语
- RRF 融合排名而非原始分数，避免 cosine 和 BM25 尺度不一致

### 2. 多级简历解析管线
- **文本 LLM**：txt/docx → LLM 提取结构化 JSON → 映射到 Layer1
- **视觉 LLM**：PDF/图片 → Vision LLM 提取 → simple JSON → Layer1
- **PaddleOCR + 规则**：离线 OCR 路径，不依赖外部 LLM API
- 按文件类型自动路由，失败可优雅降级到规则路径

### 3. 可解释匹配报告
- 每条匹配结果不只是分数，包含：
  - 硬门槛满足/缺失清单
  - 技能命中/缺失列表
  - **Delivery Alignments 表**：每条职责↔每段经历的 alignment（cosine/BM25/RRF 分数 + shared_terms）
  - 面试建议追问点
- 这是「辅助 HR 决策」而非「替代 HR 决策」的系统

### 4. 工程化实践
- Repository 模式 + Service 层分层
- 异步 SQLAlchemy + asyncpg
- 12 个测试文件覆盖 API 和检索逻辑
- Docker 一键启动（含 pgvector）
- GitHub Actions CI

## 未来可改进

- **向量检索性能**：当前是应用内暴力计算余弦，候选人数 > 5000 时需引入近似索引（pgvector ivfflat/hnsw）
- **角色轴**：job/candidate role 文本目前语义对齐度不够，权重设为 0，需更好的角色标准化方案
- **多语言**：当前 BM25 只支持中文分词，英文简历需扩展
- **前端**：仅有 Streamlit Demo，可补一个正式前端（React/Vue）
