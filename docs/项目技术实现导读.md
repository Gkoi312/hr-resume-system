# 项目技术实现导读

这份导读面向“刚接手就要快速看懂实现怎么跑起来”的开发者，重点放在本项目代码里的**入口文件/关键 service/数据落库/异步任务/语义检索增强**。尽量不讲空泛概念，直接用你在仓库里能定位到的路径与函数名。

---

## 1) 项目目标和核心能力

本项目是一个 **AI 简历筛选与候选人分析后端**，核心能力落在这些实现点上：

1. **Job（岗位/JD）管理**
   - 保存 `jobs.raw_jd_text` 与 `jobs.structured`
   - `job_service.retry_analyze_job()` 会把 `raw_jd_text` 解析为结构化字段（`app/parsers/jd_analyzer.py`）
2. **Resume（简历）上传与解析**
   - `extract_text_from_file()` 从 PDF/DOCX/TXT 抽取纯文本
   - `parse_resume_text()` 把文本抽取为结构化字段（`Resume.parsed`）
3. **Resume -> Candidate 主档回填**
   - `ResumeService.bind_candidate_from_resume()` 把解析结果“补缺写入” `candidates`，不覆盖已有非空画像（Candidate 是唯一画像来源）
4. **Matching（多维匹配 + 可解释结果落库）**
   - `MatchingService.run_matching()` 对每个候选人计算：`skill / experience / education / industry / semantic`
   - 生成结构化 `MatchExplanation` 并写入 `candidate_job_matches.explanation`
5. **RAG（语义增强）**
   - `rag_index_task` 把 Job/Candidate 语义文本 embedding 后写入 `vector_profiles`
   - 把 Candidate 的证据 chunks embedding 后写入 `resume_chunk_embeddings`
   - `MatchingService` 的 semantic 分维度读取向量并检索证据片段
6. **HR Copilot（hr-agent）**
   - `HrAgentService.ask()` 基于已落库的 `MatchExplanation` 与 job structured 做 grounded 问答
   - 可选接入外部 LLM（失败回退到 grounded 输出）
7. **异步化（Task / Worker）**
   - 耗时步骤通过 `tasks` 表入队，`python -m app.workers.task_worker` 消费执行
   - Worker 并发通过 `TaskRepository.acquire_next_pending()` 的 `SELECT ... FOR UPDATE SKIP LOCKED` 做到多实例安全

## 2) 整体架构分层

代码组织可以按“模块职责”理解为：

1. `app/api/v1/endpoints/`：HTTP 边界层
2. `app/services/`：核心业务编排（job/resume/matching/hr-agent/task 状态封装）
3. `app/database/repository/`：数据库访问层（CRUD、任务领取）
4. `app/database/session.py`：DB 事务/连接基础设施
5. `app/database/models.py`：ORM 数据模型（jobs/candidates/resumes/matches/tasks/vector_profiles/chunks）
6. `app/parsers/`：结构化抽取/解析（JD 规则解析、Resume 文本结构化）
7. `app/rag/`：语义文本构建与向量存取（profile_builder、vector_store）
8. `app/llm/`：Embedding / 可选 Chat LLM（hr-agent narrator）
9. `app/tasks/`：Task handler（在 Worker 内真正执行）
10. `app/workers/`：Task worker（轮询 tasks 表 + dispatch）

## 3) 四条主链端到端流程（job / resume / matching / task）

### 3.1 Job 主链（Job -> structured -> vector index）

你需要理解的关键点是：**structured 的生成在 `retry-analyze`，vector index 的构建在异步索引任务**。

1. Job 入口 API
   - `app/api/v1/endpoints/jobs.py`
     - `create_job()`：创建 `jobs`，必要时把状态推到 `JOB_STATUS_ANALYZING`（仅状态，不立刻解析）
     - `update_job()`：更新 `jobs`，同样可能推状态
     - `retry_analyze_job()`：真正把 `raw_jd_text` 解析为 `structured`
2. Service 编排
   - `app/services/job_service.py`
     - `retry_analyze_job()` 内部调用：`app/parsers/jd_analyzer.py:analyze_jd_text()`
     - 解析后更新 `jobs.structured`，并入队 `job_profile_index_build`
3. 异步索引构建
   - Worker 消费：`app/tasks/rag_index_task.py:handle_job_profile_index_build`
   - 生成 job 语义文本：`app/rag/profile_builder.py:build_job_semantic_text`
   - embedding：`app/llm/embedding.py:embedding_client.embed_texts`
   - 落库：`app/rag/vector_store.py:DbVectorStore.upsert_job_profile` -> `vector_profiles`

---

### 3.2 Resume 主链（上传文件 -> 文本抽取 -> parsed -> Candidate 补缺 -> 索引）

这是新同学最需要快速掌握的一条链：**上传后真正发生的步骤都在 `resumes.py / resume_service.py / text_extractor.py / resume_parser.py / bind_candidate_from_resume()`**。

1. 上传入口 API
   - `app/api/v1/endpoints/resumes.py:upload_resume`
2. 文本抽取
   - `app/parsers/text_extractor.py:extract_text_from_file`
   - `.pdf`：`pypdf.PdfReader` 逐页 `extract_text()`
   - `.docx/.doc`：`python-docx` 读取段落
   - `.txt`：utf-8 decode（失败 fallback latin-1）
3. parser 参与
   - `app/parsers/resume_parser.py:parse_resume_text(text)`
   - 输出结构化 dict，写入 `ResumeModel.parsed`
4. Resume -> Candidate 关系处理
   - `app/services/resume_service.py:ResumeService.bind_candidate_from_resume(resume_id)`
   - 逻辑核心是“候选人优先、不覆盖非空字段”
   - 最后更新 `CandidateModel` 的：`name/email/phone/education/work_experience/skills/projects/years_of_experience/summary/highest_education`
5. 触发异步索引
   - `bind_candidate_from_resume()` 末尾入队：
     - `task_type="resume_index_build"`
   - Worker 执行：`app/tasks/rag_index_task.py:handle_resume_index_build`
   - `_index_candidate()` 生成：
     - candidate general profile 向量 -> `vector_profiles`
     - candidate chunks 向量 -> `resume_chunk_embeddings`

> 注意：`/api/v1/tasks/resume-upload` 这一异步上传入口会先把文件保存到磁盘，再创建 `resume_upload` task，让 Worker 在后端走同样的 extract/parse/bind 逻辑。

---

### 3.3 Matching 主链（五维评分 -> semantic RAG -> MatchExplanation -> 落库）

1. 入口 API
   - `app/api/v1/endpoints/matching.py`
     - `run_matching()` -> `matching_service.run_matching(job_id, candidate_ids, delete_old=True)`
2. Service 评分编排
   - `app/services/matching_service.py:MatchingService.run_matching`
   - 对每个 candidate 依次计算：
     - `skill_s, skill_details = _skill_score(job_struct, profile)`
     - `exp_s, exp_details = _experience_score(job, job_struct, profile)`
     - `edu_s, edu_details = _education_score(job, job_struct, profile)`
     - `ind_s, industry_details = _industry_score(job_struct, profile)`
     - `sem_s, sem_details = _compute_semantic_scores_for_candidates(...)[candidate.id]`
3. 总分与解释
   - 总分：`_overall_score(...)`（按 `WEIGHT_*` 加权）
   - pros/cons/recommendation：`_pros_cons_recommendation(...)`
   - `MatchExplanation`：
     - 先 `_build_match_explanation(...)` 生成结构化解释
     - 再把 semantic 的 `semantic_status` 与 `semantic_evidence` 填进去
4. 落库
   - `await match_repository.create(...)`
   - `match_repository.create()` 写入 `CandidateJobMatchModel` -> 表 `candidate_job_matches`

---

### 3.4 Task 主链（写入 tasks 表 -> Worker 领取 -> handler 调 service/rag/parser）

Task/Worker 的关键作用不是“改变业务分层”，而是把执行时机与并发做成可控的后台系统。

1. 写入 tasks 表（入队）
   - `app/api/v1/endpoints/tasks.py`：显式创建任务
   - `app/services/*_service.py`：业务事件发生后“最佳努力”入队索引任务
2. Worker 调度执行
   - `app/workers/task_worker.py`
     - `worker_loop()`：轮询 pending task 并在协程并发下 dispatch
     - `dispatch_task(task)`: 根据 `task.task_type` 选择对应 handler
3. 并发安全领取
   - `app/database/repository/task_repository.py:acquire_next_pending`
   - 用 `select(...).with_for_update(skip_locked=True)` 防止多实例重复消费同一个 task
4. handler 复用原有业务组件
   - `resume_upload` -> `app/tasks/resume_task.py` 里调用 `resume_service` + `text_extractor` + `resume_parser`
   - `matching_run` -> `app/tasks/match_task.py` 里直接调用 `matching_service`
   - `*_index_build` -> `app/tasks/rag_index_task.py` 里调用 rag/profile_builder/embedding/vector_store

## 4) Candidate、Resume、Job、Match 的数据关系

用 ORM 表关系理解最直观：

1. `JobModel`（表 `jobs`）
   - 一份 job 对应多个匹配结果：`JobModel.matches -> CandidateJobMatchModel`
2. `CandidateModel`（表 `candidates`）
   - 一份 candidate 对应多份 resume：`CandidateModel.resumes -> ResumeModel`
   - 一份 candidate 对应多条匹配结果：`CandidateModel.matches -> CandidateJobMatchModel`
3. `ResumeModel`（表 `resumes`）
   - 每条 resume 属于一个 candidate：`resumes.candidate_id -> candidates.id`
   - resume 内含解析快照：`resumes.parsed`
4. `CandidateJobMatchModel`（表 `candidate_job_matches`）
   - 一对 `(job_id, candidate_id)` 代表一条匹配记录
   - 包含各子分：`overall_score/skill_score/experience_score/education_score/semantic_score/industry_score`
   - 包含解释：`explanation`（JSON）

核心语义关系（你要牢记）：
- **Candidate 是唯一画像来源**：matching 评分与 profile 构建都以 `CandidateModel` 字段为准。
- **Resume 是证据输入与补缺输入**：`ResumeService.bind_candidate_from_resume()` 只把 parsed 信息用于填补 candidate 的空字段。

## 5) RAG、parser、hr_agent 在系统中的位置

### 5.1 parser（结构化抽取/解析）
- Job structured：`app/parsers/jd_analyzer.py:analyze_jd_text`
- Resume parsed：`app/parsers/resume_parser.py:parse_resume_text`
- 文本提取：`app/parsers/text_extractor.py:extract_text_from_file`

它们提供的是“可审计、可追踪的结构化字段”，匹配规则依赖这些结构化字段中的候选人主档字段与 job structured。

### 5.2 RAG（语义增强与证据检索）
- 索引落库：`app/tasks/rag_index_task.py` 调用
  - `app/rag/profile_builder.py` 生成 semantic text / chunks
  - `app/llm/embedding.py` 生成向量
  - `app/rag/vector_store.py` 写入 `vector_profiles` 与 `resume_chunk_embeddings`
- matching semantic 分：`app/services/matching_service.py:_compute_semantic_scores_for_candidates`
  - 从 `vector_profiles` 读取 job/candidate profile 向量
  - 从 `resume_chunk_embeddings` 检索证据 snippets
  - 将语义相似度与证据覆盖度融合成 `semantic_score`

### 5.3 hr_agent（已移除）

历史上的 Copilot 接口 `/hr-agent/ask` 与 `HrAgentService` 已从代码库删除；HR 侧以 matching 返回的 `MatchExplanation` 与列表为主。通用 Chat 客户端见 `app/llm/chat_client.py`，无参默认读取 `RESUME_LLM_*`（与简历文本 LLM 一致），JD 等路径使用 `JOB_LLM_*` 等。

## 6) 同步调用和异步任务的边界

最容易混淆的是：哪些操作发生在 API 请求里，哪些交给 Worker。

1. **同步路径（API 内执行）**
   - 简历：`app/api/v1/endpoints/resumes.py:upload_resume`
     - 上传 -> extract_text_from_file -> parse_resume_text -> save_parsed_resume -> bind_candidate_from_resume
     - API 返回时 resume 状态已经推进到 `RESUME_STATUS_CANDIDATE_BOUND`
   - job 的创建/更新通常只写 `jobs` 并入队索引任务，真正 structured 解析在 `retry-analyze` 中发生
   - matching 的同步入口是 `app/api/v1/endpoints/matching.py:run_matching`
2. **异步路径（Task/Worker）**
   - 简历异步上传：`app/api/v1/endpoints/tasks.py:create_resume_upload_task` 创建 `resume_upload` task
     - Worker：`app/tasks/resume_task.py:handle_resume_upload`
   - matching 异步：创建 `matching_run` task，Worker 调 `handle_matching_run` -> `matching_service.run_matching`
   - 向量索引构建：`*_index_build` task，Worker 调 `app/tasks/rag_index_task.py`

一句话总结：
- **API 同步路径负责“输入处理与直接落库”**；
- **Worker 异步路径负责“耗时计算与索引构建/批任务”**；
- 两者都复用相同的 service/parser/rag 组件。

## 7) 最值得先读的 10 个核心文件（以及为什么重要）

1. `app/database/models.py`
   - 用它先建立“Job/Candidate/Resume/Match/Task/Vector”的真实字段与关系认知
2. `app/services/resume_service.py`
   - Resume -> Candidate 主档回填的合并规则全在这里（Candidate 是唯一画像来源）
   - 并且在 bind 完成后入队 `resume_index_build`
3. `app/parsers/text_extractor.py`
   - PDF/DOCX/TXT 文本抽取的实际实现，决定 parsed 的上游质量
4. `app/parsers/resume_parser.py`
   - Resume 的 parsed 字段如何被抽取（skills/education/work_experience/...）
5. `app/services/matching_service.py`
   - 匹配评分与解释生成的核心 orchestration：skill/experience/education/industry/semantic + overall
6. `app/rag/vector_store.py`
   - semantic 分如何读取向量、如何检索证据 chunks、如何落库 profiles/chunks
7. `app/tasks/rag_index_task.py`
   - 所有向量索引构建（job/candidate/resume）的执行入口
8. `app/workers/task_worker.py`
   - Worker 轮询 + dispatch + 并发控制（决定任务何时跑）
9. `app/services/job_service.py`
   - job structured 的解析入口与索引入队逻辑
10. `app/services/hr_agent_service.py`
   - grounded 问答如何读取匹配解释与 job/candidate 信息；可选 LLM narractor 与回退机制

## 9) 新同学 2 小时读码路线（可直接照做）

下面是一个很“可执行”的 2 小时计划，目标是你能讲清楚系统怎么跑通：

### 0-20 分钟：建模与关系
- 打开 `app/database/models.py`
- 找到并理解：`JobModel / CandidateModel / ResumeModel / CandidateJobMatchModel / TaskModel / VectorProfileModel / ResumeChunkEmbeddingModel`

### 20-40 分钟：Resume 上传与 Candidate 回填
- 读 `app/api/v1/endpoints/resumes.py:upload_resume`
- 重点读 `app/services/resume_service.py:bind_candidate_from_resume`
- 你需要能回答：为什么 Candidate 是唯一画像来源、代码怎么“不覆盖非空字段”

### 40-60 分钟：RAG 索引构建落库
- 读 `app/tasks/rag_index_task.py`（resume_index_build / candidate_index_build / job_index_build）
- 读 `app/rag/vector_store.py` 中的 `upsert_job_profile / upsert_candidate_profile / upsert_resume_chunks`

### 60-80 分钟：Matching 五维评分与解释落库
- 读 `app/services/matching_service.py:run_matching`
- 找到并理解五个子分函数：`_skill_score / _experience_score / _education_score / _industry_score / _compute_semantic_scores_for_candidates`
- 再读 `_build_match_explanation` 看 explanation 的结构来源

### 80-100 分钟：异步任务执行机制
- 读 `app/api/v1/endpoints/tasks.py`（你如何创建 tasks）
- 读 `app/workers/task_worker.py`（dispatch 与并发）
- 读 `app/database/repository/task_repository.py:acquire_next_pending`（SKIP LOCKED 并发安全）

### 100-120 分钟：补齐 job structured 与 hr-agent
- 读 `app/services/job_service.py:retry_analyze_job` + `app/parsers/jd_analyzer.py`
- 读 `app/services/hr_agent_service.py:ask`（grounded 与可选 LLM narrator）

到这里你应该已经能在不看外部文档的前提下，描述整个系统从上传简历到匹配出解释，再到 hr-agent 回答的闭环。
